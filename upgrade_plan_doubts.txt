**2. The RBox-SSDD angle convention needs verification before you write a single line of training code.**

Ultralytics YOLO-OBB expects angle in degrees, range `[0, 90)`, defined as rotation from the positive x-axis to the longer edge. RBox-SSDD uses `[cx, cy, w, h, angle]` but the angle definition and range differ across papers and releases. The UPGRADE_PLAN says "verify by visual overlay" — this is correct but needs to be your literal first task, not an afterthought. A wrong angle convention will train silently and produce a model that looks like it's learning but isn't.

Write a validation script before converting all labels:

```python
import cv2
import numpy as np

def draw_rbox(img, cx, cy, w, h, angle_deg):
    """Visualize one rotated box to verify convention."""
    rect = ((cx, cy), (w, h), angle_deg)
    box = cv2.boxPoints(rect).astype(np.int32)
    cv2.drawContours(img, [box], 0, (0, 255, 0), 2)
    return img
```

Spot-check 20 images before running the full conversion.

**3. The training config disables HSV but your `augment_data.py` applies brightness and contrast augmentations.**

When you train with Ultralytics, its internal augmentation pipeline will run on top of your already-augmented images. You'll get double-augmentation for brightness/contrast unless you either: (a) pass raw images to Ultralytics and let it handle augmentation, or (b) disable Ultralytics internal augmentation for the photometric transforms while keeping geometric ones.

Cleanest solution: pass raw (non-augmented) SSDD images to Ultralytics training and let it handle all augmentation via the YAML config. Your `augment_data.py` was built for the COCO static dataset approach — it's less relevant when training with Ultralytics which does augmentation on-the-fly.

### Significant — Will affect result quality

**4. The cross-domain test set is 8 chips with 13 ships.**

This is too small to report reliable mAP. At 8 images, a single false positive or false negative swings mAP by ~10%. You need to annotate more Umbra chips before calling the cross-domain result meaningful.

Practical fix: from your 459 generated chips, go back and annotate all chips that contain ships — not just the 8 you submitted for the assignment. You likely have 20-40 more annotated chips possible from the existing data. This is 2-3 hours of work and transforms your cross-domain evaluation from anecdotal to defensible.

**5. Heading estimation from OBB angle needs explicit handling.**

The UPGRADE_PLAN mentions `heading_degrees` in the GeoJSON output but OBB angle has a 180-degree ambiguity — the model can't distinguish bow from stern. The plan doesn't address this. Either:
- Document the ambiguity explicitly (heading is ±180°, report as bearing range)
- Use wake direction to resolve it (if visible in the chip)
- Report it as vessel orientation, not heading

Don't claim heading without addressing this — a reviewer at GalaxEye will catch it immediately.
